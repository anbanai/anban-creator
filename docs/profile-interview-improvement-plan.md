# 人设访谈：先接住用户信息，再问一个关键问题

状态：2026-10-26 待讨论方案。本次代码先修复首条消息丢失，不修改 Harness 提示词或画像数据结构。

## 目标与交互

用几分钟建立能支撑首次创作的初步人设，而非一次填满所有维度。五分钟是体验目标，不是强制结束或性能承诺。

1. **先听完。** 用户已经讲了一大段，就先提炼已有事实，直接接话；只有没提供实质信息时才使用欢迎开场。不能再次问已经回答的问题。
2. **一轮一个关键缺口。** 优先搞清楚“你是谁、服务谁、希望内容带来什么、有什么可信的经验或特点”。根据已有信息跳过已知项。表达风格、账号资料等非关键项可稍后补充。
3. **短回复。** 日常回应以 1–2 句、约 60–120 字为目标：一句回应理解，必要时再问一个问题。只在最终摘要或用户主动要求时展开，不每轮输出整份分析。
4. **问题容易答。** 少问“你的差异化定位是什么”，多问“客户为什么会选你”。用户卡住时给 2–3 个贴合其业务的例子，允许“不确定／跳过”；不同时问受众、预算、平台和风格。
5. **看到积累。** 侧边画像只显示已确认的简要描述与关键待补项；明确区分事实、建议和未知。用“已可开始创作／还需明确受众”等状态，不用问了几轮计算虚假的完整度。
6. **随时校正、尽早创作。** 基础信息足够就给一份短摘要和“开始创作”，画像不以结束访谈为前提。用户继续补充时只更新相关部分。

例：用户已说明是茶厂负责人、面向茶叶店主、希望建立信任。

> 我记下了：你想用茶厂一线经验，帮助茶叶店主选好茶、建立信任。客户向你拿货时，最认可你的哪一点？

不要再问“你是做什么的”“你的目标受众是谁”，也不要先展开全部平台能力介绍。

## 实施边界

- 在 `harness/packs/project-creator/agent.dsh.yml` 与 `harness/skills/project-creator-client-discovery/SKILL.md` 的规范中统一首轮优先消化输入、短回复与停止追问条件；按插件生成规则同步派生产物与版本，单独提 PR。
- 不增加固定问卷、不让前端猜测画像事实、不让 Agent 绕过用户确认写入正式画像。继续使用已有 Server 暂存、确认和保存机制。
- 下一轮补可观测指标：首次有效回应耗时、重复提问率、用户轮次、关键事实保留率、首次创作进入率。实际模型质量用固定案例验收，不以提示词包含某句话代替效果验证。
- 验收案例至少包含：长段首述、只有一句话、纠正旧信息、临时插问、答不上来、已有画像更新。检查事实是否保留、是否只问关键缺口、是否简短且易答。

## 上下文可靠性边界

本次确定修复：首页工作区启动期间，首条用户消息进入 `queuedPrompt` 后未被发送给 Runtime，反而发送默认开场白。修复后启动先投递原消息，尚无用户消息时等待输入，不抢先启动开场轮次。

另一个独立风险：服务重启或逻辑会话替换目前只恢复 Server 草稿快照，不保证尚未进入草稿的逐轮对话恢复。此轮不把聊天记录塞进画像或 checkpoint，也不宣称已解决所有断线恢复。后续应明确独立的会话持久化、用户与人设隔离、恢复来源及页面恢复提示，再单独评审实现。
